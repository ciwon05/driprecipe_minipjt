
# SERVICE · 주말 여행지 추천 Agent

## 1. 사용자·문제·가치
- 누구를 위한 서비스인가: 임직원 복지 프로그램을 운영하는 인사팀 담당자
- 어떤 문제를 푸는가: 주간에 고생한 임직원에게 가족 구성에 맞는 주말 여행지를 추천하려면 담당자가 매번 여행지·교통비·소요시간·주변 명소·주변 맛집을 일일이 찾아야 한다
- 지금은 어떻게 해결하나: 인사팀이 수기로 검색하거나, 가족 구성과 무관한 획일적인 안내문을 보낸다
- 이걸로 뭐가 좋아지나: 담당자가 대상 임직원과 대략적인 지역(정확한 목적지일 수도, "강원도"처럼 넓은 지역일 수도 있음)을 넣으면 맞춤 여행지·교통비·소요시간 견적·근처 가볼만한 곳·주변 맛집이 한 번에 요약되어 나온다.

## 2. 서비스 확장 관점
- 사내 기여: 인사팀이 복지성 여행 추천을 준비하는 시간을 줄이고, 임직원 체감 복지 수준을 높인다.
- 규모: 사내 인사팀 담당자(소수)가 매주 대상 임직원(팀 단위, 주당 수십 명 규모)에게 반복 사용
- 대체제와 차별점: 획일적 안내문은 가족 구성을 반영하지 못한다. — 이 Agent는 인원수·아이 동반 여부에 따라 후보를 다르게 추천한다.

## 3. 사용 예상 도구·데이터
- 도구:
  - 도구 중 Search_Employee는 미리 만들어 둔 json 더미 데이터에서 조회하고, Traffic_Calculator는 별도 조회 없이 계산만 하며, Recommend_place와 Nearby_Restaurant은 카카오 디벨로퍼스 API를, Price_Time은 한국도로공사 공공데이터포털 API를 호출해 조회한다.
  - (Search_Employee)이름(또는 임직원ID)으로 임직원 가족 구성 조회
    동명이인이 있으면 상세 정보 대신 해당 이름의 임직원ID 후보 목록을 반환해, 담당자에게 임직원ID를 추가로 확인한다
  - (Recommend_place)담당자가 입력한 지역(정확한 목적지 또는 넓은 지역)의 명소 중, Search_Employee에서 조회한 가족 구성(구성원별 관계)에 맞고 최근 언급이 많은 곳 검색 (완전 무료 — 카카오 디벨로퍼스 REST API 키 하나로 로컬 API·다음 검색 API 둘 다 사용)
    가족 구성에 따라 검색어에 아래 키워드를 더한다 (해당 없는 모든 경우의 기본값은 "가족여행" —
    예: 성인 자녀만 있는 가족도 이 기본값을 쓴다):
      - 미성년 자녀가 있으면 "아이와 가볼만한"
      - 배우자만 있고 자녀가 없으면(커플) "커플 여행"
      - 가족 구성원이 없으면(1인 가구) "혼자 가기 좋은"
    1) 카카오 로컬 API 키워드 장소 검색(`https://dapi.kakao.com/v2/local/search/keyword.json`)에
       `category_group_code=AT4`(관광명소 고정 코드)를 함께 넘겨 "담당자가 입력한 지역 + 위
       키워드"로 그 지역의 명소 후보를 가져온다. 카테고리를 요청 파라미터로 직접 지정하므로
       응답 문자열을 따로 필터링할 필요가 없다. 결과가 없으면 키워드를 빼고 지역명만으로 한 번
       더 검색한다(category_group_code는 유지)
    2) 후보별로 카카오 다음 검색 블로그 API(`https://dapi.kakao.com/v2/search/blog`)에
       "후보명 여행 후기"로 조회해, 응답의 meta.total_count(검색결과 총 개수)를 언급 건수로 사용한다
    3) 언급 건수가 많은 순으로 정렬해 상위 1~2곳을 '추천 명소'로 제시하고, 나머지는 '그 외 가볼만한 곳'으로 함께 안내한다. 이 값은 실제 평점이 아니라 블로그 언급 빈도이므로, 답변에도
       "평점이 아니라 최근 블로그 언급이 많은 곳 기준"이라는 점을 명시한다.
    일치하는 결과가 없으면 지어내지 않고 '데이터 없음'을 반환한다.
    로컬 API 응답의 좌표(x=경도, y=위도, 십진수라 변환 불필요)도 함께 보관해 Price_Time에서 재사용한다 — 별도 좌표 조회가 추가되는 것은 아니다.
    담당자가 입력한 지역이 넓은 지역이어도, 지역 검색 결과로 나온 '추천 명소'는 항상 구체적인 장소(주소 있음)이므로 이후 단계의 목적지는 항상 명확하게 정해진다.
  - (Price_Time)'추천 명소' 기준 통행료·거리·소요시간 조회
    한국도로공사 공공데이터포털 "영업소간 통행요금 조회" API
    (`data.go.kr`, 완전 무료 — 개발단계는 자동승인) 사용. 통행료는 1종(승용차) 기준으로 조회한다
    출발지는 '삼성SDS타워WESTCAMPUS' 좌표에서, 도착지는 Recommend_place가 이미 갖고 있는 '추천 명소'의 좌표(lat/lng)에서, 각각 전국 영업소 좌표 목록(`data/Ex_Office_Coor.json`) 중 직선거리가 가장 가까운 영업소를 계산해 찾는다(텍스트 지역명 매칭이 아니라 좌표 기준 최근접 계산이므로 전국 어디든 커버된다)
    응답의 통행료, 거리, 소요시간을 그대로 사용한다. 단, 이 값은 두 영업소 사이 고속도로 구간만 포함하고 사무실↔진입 나들목, 출구 나들목↔추천 명소 구간(일반도로)은 포함하지 않는다는 점을 답변에도 명시한다. 이 API에는 연료비 필드가 없어 Traffic_Calculator에서 거리를 기반으로 별도 계산한다
  - (Nearby_Restaurant)'추천 명소' 주변(반경 1.5km) 맛집 조회 (완전 무료 — Recommend_place와
    같은 카카오 REST API 키 재사용, 새 인증키 불필요)
    카카오 로컬 API 카테고리 검색(`https://dapi.kakao.com/v2/local/search/category.json`)에
    `category_group_code=FD6`(음식점 고정 코드)와 Recommend_place가 반환한 '추천 명소'의
    좌표(lat/lng), 반경(1.5km), `sort=distance`를 넘겨 가까운 순으로 후보를 가져온다.
    후보별로 카카오 다음 검색 블로그 API로 언급 건수를 조회해 그중 가장 많이 언급된 곳
    하나를 추천 맛집으로 고른다 — 이것도 평점이 아니라 언급 빈도 기준이다.
    일치하는 결과가 없으면 지어내지 않고 '데이터 없음'을 반환한다.
  - (Traffic_Calculator)교통비 계산기: 왕복 교통비 = (통행료 + 거리 × 유류비 단가) × 2
    유류비 단가는 원/km 고정 상수(예: 150원/km)로 둔다

- 데이터:
  - 임직원 정보 JSON (더미: 임직원 이름, 임직원ID, 부서명, 이메일주소, 핸드폰번호, 가족정보(구성원별 이름, 관계[배우자/아들/딸/기타], 나이))
  - 전국 고속도로 영업소 좌표 JSON (더미: 영업소명, 영업소코드, 좌표) — 공공데이터포털의 전국 영업소 목록을 기반으로 구성
  - 공공데이터포털(data.go.kr) 한국도로공사 API, 카카오 디벨로퍼스 REST API 키는 `.env`에서 읽고 코드에는 적지 않는다

## 4. 서비스 정책 (가드레일 요약)
- 담당자가 지역을 입력하지 않으면 임의로 지역을 정하지 않고 어느 지역으로 찾을지 되묻는다.
- 등록되지 않은 명소·맛집은 지어내지 않고 실제 존재하는 후보만 안내한다.
- 검색 시 조회가 없는 경우 지어내거나 추정하지 않고 '데이터 없음'이라고 표시한다.
- 인사팀 담당자는 모든 임직원의 가족 정보를 조회할 수 있다. 답변은 담당자가 지정한 대상 임직원 1인에 대해서만 작성한다.
- 동명이인 임직원을 조회할 경우, 임직원ID로 대상을 확정한 뒤 진행한다.
- 가족 구성원의 나이·관계는 추천 판단(아이 동반 여부 등)에 내부적으로 사용하되, 최종 답변에는 대상 임직원 본인 이름만 노출하고 가족 구성원 개별 이름·나이·관계는 노출하지 않는다(예: "배우자, 자녀 2명" 정도로만 표현). 나이는 숫자("6세")든 한글 숫자("여섯 살")든 어떤 형태로도 답변에 쓰지 않는다.
- 교통비는 항상 "추정치"임을 명시한다(고속도로 통행료와 유류비를 포함한 값). 실제 결제·예약은 Agent가 직접 실행하지 않는다.
- 명소·맛집 추천 근거는 평점이 아니라 최근 블로그 언급 빈도임을 답변에 명시한다.
- 가족 구성원은 성이든 이름만이든 실제 이름으로 답변에 노출하지 않는다. 항상 관계로만 지칭한다(예: 배우자님, 아드님, 따님). 대상 임직원 본인 이름만 답변에 써도 된다.
- 최종 답변은 대상 임직원 이름을 넣어 한 주간 고생했다는 인사로 시작하고, 이번 주말 가족과 함께 '추천 명소'로 다녀올 것을 권유하며 추천 사유를 함께 제시한다(블로그 언급 건수 같은 구체적 숫자는 적지 않는다). 맛집·교통비·소요시간은 본문이 아니라 맨 마지막에 '참고 자료' 제목 아래 마크다운 표(왕복 교통비/편도 소요시간/주변 맛집 순서로 세 행)로 정리하고, 그 뒤에 "위 교통비는 고속도로 통행료와 유류비를 포함한 추정치 입니다."와 "명소 추천 근거는 평점이 아니라 최근 블로그 언급 빈도입니다."라는 고정 안내 문구를 덧붙인다(이 두 문장은 매번 같은 문구로 고정한다).

## 5. 성공 기준
- 평가 세트: `evaluation/test_queries.csv` 14건
- 판정 방식: 실시간 조회 데이터라 "기대 가격"을 미리 고정하지 않고, 그 실행에서 도구가 실제로 반환한 원본 값(raw 명소 후보·맛집·통행료·거리·소요시간) 대비 최종 답변의 내용·계산이 일치하는지를 사람이 항목별로 채점한다
- 항목 구성과 pass 조건
  - 정상 케이스 10건 (목적지를 정확히 지정한 경우 5건 + 넓은 지역만 준 경우 5건, 가족 구성도 아이 동반/커플/1인 가구/성인 자녀만 있는 가족을 섞어서 구성): 최종 왕복 교통비가 (통행료 + 거리 × 유류비 단가) × 2 공식대로 그 실행에서 한국도로공사 API가 반환한 원본 통행료·거리를 기준으로 정확히 계산되어 있고, 가족 구성에 맞는 검색 키워드(아이와 가볼만한/커플 여행/혼자 가기 좋은/가족여행)가 반영되어 있고, 참고 자료 표에 그 실행에서 조회된 주변 맛집 이름이 정확히 들어가 있으면 pass
  - 존재하지 않는 임직원/지역 질문 2건: 지어낸 명소·임직원 정보 없이 '데이터 없음' 또는 등록되지 않았다는 안내만 나오면 pass
  - 동명이인 임직원 질문 2건: 임직원ID를 추가로 확인한 뒤 진행하면 pass
- 14건 중 12건 이상 pass
